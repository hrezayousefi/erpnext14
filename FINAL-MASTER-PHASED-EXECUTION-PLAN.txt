بخش الف — قوانین ثابت حاکم بر همهٔ فازها
--------------------------------------------------------------------------------
Q01. هیچ داده یا رفتار تولیدی از طریق Odoo shell/console تعاملی ساخته نمی‌شود؛
     همه‌چیز در قالب ماژول نصب‌شونده (`models/`, `security/`, `data/`, `views/`,
     `i18n/`) است که با `-i`/`-u` نصب/ارتقا و در Git ثبت می‌شود.
Q02. ترتیب نصب ماژول‌ها قفل است (یک‌طرفه، بدون حلقه):
        itr_base → itr_notify → itr_core → itr_transport → itr_reports →
        itr_integration
Q03. کاربر `Administrator` فاقد هرگونه نقش کسب‌وکاری است و در هیچ سناریوی
     تستی برای اثبات درستی فرآیند استفاده نمی‌شود (تست منفی این بند در هر
     فاز اجباری است).
Q04. هر فاز حداقل یک آزمون مثبت و یک آزمون منفی برای هر مجوز/گارد تازه دارد.
Q05. نام‌های فنی (فیلد/مدل/اکشن/منو) همیشه ASCII (snake_case)؛ برچسب فارسی
     فقط از فایل ترجمه (`i18n/fa.po`).
Q06. منطق قطعی کسب‌وکار فقط در متد مدل پایتون (`models/*.py`) یا سرویس داخل
     ماژول؛ هرگز صرفاً در جاوااسکریپت کلاینت یا Server Action موقتی و مستندنشده.
Q07. هیچ متن پیامک، گیرنده، زمان هشدار، کلید API، رمز عبور یا مسیر مطلق
     سیستم‌عامل داخل کد هاردکد نمی‌شود؛ همه از `ir.config_parameter` یا مدل
     تنظیمات ماژول می‌آیند.
Q08. تا سبز نشدن معیار پذیرش (Gate) یک فاز، فاز بعدی آغاز نمی‌شود؛ هیچ فازی
     «تقریباً کامل» تحویل داده نمی‌شود — موارد ناقص صریح و Gate قرمز می‌مانند.
Q09. بعد از هر فاز مهم: ارتقای ماژول (`-u`)، اجرای تست‌های خودکار همان فاز،
     پاک‌سازی کش دارایی‌ها (assets)، و ثبت Git commit با تگ نسخهٔ فاز.
Q10. در فازهای حساس (۶، ۹ و ۱۱): پشتیبان کامل (`pg_dump` + پوشهٔ filestore)
     پیش از اجرای تغییرات بزرگ، به‌همراه یک آزمون بازیابی (Restore) واقعی.
Q11. نام‌های فنی وضعیت (Selection/State) که در فاز ۴ و فاز ۶ قفل می‌شوند، در
     فایل `ARCHITECTURE_DECISIONS.md` ثبت و از آن پس بدون Migration رسمی
     تغییر نمی‌کنند (رجوع G10 سند نیازمندی).
Q12. هیچ رمز یا دادهٔ عملیاتی واقعی داخل مخزن Git نمی‌رود؛ فقط ساختار و
     دادهٔ نمونهٔ صریحاً برچسب‌خورده با پیشوند «TEST».
Q13. مدل‌های هستهٔ Odoo (`res.partner`, `product.template`, `res.company`,
     `fleet.driver`, `fleet.vehicle`) در حد امکان با ارث‌بری (`_inherit`)
     گسترش داده می‌شوند؛ ساخت مدل موازی برای همان مفهوم ممنوع است.
Q14. هر فاز باید یک «نقشهٔ استفادهٔ مجدد» مستند کند: چه فیلد/مدلی از فاز قبل
     بازاستفاده شد و چرا مدل موازی ساخته نشد.
Q15. هر فاز باید یک اسکریپت verify مستقل داشته باشد که با کاربر واقعی (نه
     sudo) اجرا شود و حداقل یک «تست منفی» داشته باشد.

سه قانون طلایی توسعهٔ آینده (در تمام فازها رعایت می‌شود):
   T1. هیچ قابلیت به‌تعویق‌افتاده‌ای حق ندارد راه توسعهٔ آینده را ببندد.
   T2. هر ارتباط با سیستم بیرونی فقط از مسیر آداپتور/سرویس انجام می‌شود.
   T3. هیچ فیلد یا رابطه‌ای نباید طوری قفل شود که رشد آینده را محدود کند.

فهرست ممنوعه‌های دائمی (در هیچ فازی، حتی به‌صورت آزمایشی، ساخته نمی‌شوند):
   واتساپ، فرم‌ساز/گزارش‌ساز/داشبوردساز عمومی، چت سازمانی مستقل، نقشهٔ تعاملی
   زنده، BI بیرونی مستقیم، شبیه‌سازی داخلی سپیدار، اختراع نام تازه برای
   وضعیت‌های قفل‌شدهٔ حمل، موتور دوم برای تقویم/SLA/سود/KPI/Task.

هدف: انتقال به سرور اصلی، ورود دادهٔ پایهٔ واقعی، و قطع رسمی فرآیندهای
کاغذی/موازی.
پیش‌نیاز: فاز ۱۲ سبز.

چک‌لیست:
[ ] 13.1  تگ نسخهٔ Git برای هر شش ماژول (`itr_base`, `itr_notify`, `itr_core`,
          `itr_transport`, `itr_reports`, `itr_integration`).
[ ] 13.2  راه‌اندازی سرور خام تولید با همان ماتریس نسخهٔ ثبت‌شده در فاز ۰.
[ ] 13.3  دریافت ماژول‌ها از Git خصوصی و نصب به ترتیب وابستگی قفل‌شدهٔ Q02.
[ ] 13.4  مسیر A (دیتابیس تازه + Data Files) یا مسیر B (Restore از پشتیبان
          UAT تأییدشده — هرگز از دیتابیس توسعهٔ آلوده).
[ ] 13.5  تنظیم کلیدهای واقعی درگاه پیامک و سایر اعتبارنامه‌ها فقط روی سرور
          تولید (هرگز در Git).
[ ] 13.6  پشتیبان کامل پیش از Go-Live.
[ ] 13.7  `test_mode` فقط پس از تأیید صریح مدیر پروژه و یک ارسال آزمایشی
          کنترل‌شده خاموش می‌شود؛ سپس `sms_master_enabled` روشن می‌شود.
[ ] 13.8  یک خرید و یک فروش واقعی با نظارت مستقیم مدیران پروژه.
[ ] 13.9  پس از بستن موفق اولین معاملهٔ واقعی، فرآیندهای سنتی/کاغذی موازی
          رسماً متوقف و سامانه به‌عنوان تنها مرجع حقیقت عملیات اعلام می‌شود.

معیار پذیرش فاز ۱۳ (Gate 13 — پایان پروژه):
[ ] حداقل یک خرید و یک فروش واقعی به‌طور کامل بسته شده‌اند.
[ ] هیچ رمزی در Git نیست (اسکن نهایی مخزن انجام شده).
[ ] مسیر ارتقای آینده (بخش ۱۶ و ۱۷ سند نیازمندی) بدون نیاز به بازنویسی
    ساختاری باز است.


================================================================================
پیوست الف — نقشهٔ اتصال فازها (خلاصهٔ توالی نهایی)
================================================================================
فاز۰(محیط) → فاز۱(itr_base) → فاز۲(itr_notify) →
فاز۳(سازمان/امنیت/داده‌پایه) → فاز۴(Trade Case+تأییدات+امضا) →
فاز۵(ریزفاکتور+ایجاد خودکار حمل) → فاز۶(عملیات حمل+هزینهٔ داینامیک+پرداخت+
بستن) → فاز۷(تثبیت مجوزها/SoD) → فاز۸(کارتابل/Workspace/داشبورد) →
فاز۹(گزارش/چاپ/اکسل — سنگین‌ترین فاز) → فاز۱۰(سیم‌کشی اعلان/SLA) →
فاز۱۱(اسکلت سپیدار، اختیاری تا سطح Dry-Run) → فاز۱۲(UAT جامع) →
فاز۱۳(Go-Live)

هیچ فازی نباید قبل از سبزشدن معیار پذیرش فاز قبلی آغاز شود. پس از هر فاز:
گزارش وضعیت باید صریح باشد — یا «فاز X تمام شد» یا «فاز X گیر کردم: دلیل...» —
هرگز ادعای درصد پیشرفت مبهم بدون چک‌لیست سبز.


================================================================================
پیوست ب — چک‌لیست تحویل اجباری هر فاز
================================================================================
[ ] Scope انجام‌شده با شناسهٔ نیازمندی (REQ/BR/SEC/VAL/OPS/FIN/NOT/REP/XLS/UX/NFR).
[ ] Scope انجام‌نشده/خارج فاز، با دلیل صریح.
[ ] فایل‌های ایجاد/تغییرکرده + external idها و migrationها.
[ ] ماتریس دسترسی تغییرکرده.
[ ] تست‌های unit/integration/access/UAT و خروجی واقعی.
[ ] تست نصب تمیز و ارتقای تکراری (Idempotency)؛ شمار رکورد قبل/بعد.
[ ] خطاهای log و هشدارهای باقی‌مانده.
[ ] Backup id/checksum و نتیجهٔ Restore در فازهای حساس.
[ ] دستور Rollback آزموده‌شده.
[ ] Commit hash/tag.
[ ] Gate با وضعیت سبز/قرمز؛ بدون عبارت مبهم «تقریباً».


================================================================================
پیوست ج — توقف‌های اجباری (اگر هرکدام رخ داد، فاز متوقف است)
================================================================================
[ ] نیاز دامنه‌ای متناقض یا بدون منبع حقیقت.
[ ] Migration مخرب بدون backup و rollback.
[ ] استفاده از سوپریوزر برای عبور از قانون کسب‌وکاری.
[ ] ساخت رکورد تکراری در اجرای دوم (نقض Idempotency).
[ ] Mismatch عدد فرم و گزارش.
[ ] Bypass شدن اکشن از RPC.
[ ] Secret یا دادهٔ شخصی در Git/log.
[ ] ارسال واقعی ناخواسته SMS.
[ ] از دست رفتن merge/فرمول/قالب در اکسل.
[ ] شکست Restore یا نبود شاهد تست.
